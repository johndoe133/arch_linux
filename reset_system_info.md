## 3. Storage & swap

- `/swapfile` — 20 GiB, mode 0600, created with `mkswap -U clear --size 20G --file /swapfile`
- `/etc/fstab`: `/swapfile none swap defaults,pri=-2 0 0`
  - **Effective priority is −1**, not −2. The kernel auto-assigns; `pri=-2` is not honoured.
    Harmless — zram is priority 100, so ordinary paging still goes to zram and the
    swapfile stays empty and available for a hibernation image.
- `zram0` — 15 G, priority 100, CachyOS default, untouched. systemd ignores zram
  devices when choosing a hibernation target, so it cannot interfere.
- **Resume path needs no configuration.** `HOOKS` contains `systemd`, so systemd writes
  the `HibernateLocation` EFI variable at hibernate time and reads it back on the next
  boot. No `resume` hook, no `resume=`, no `resume_offset=`.
- If resume ever fails with "image not found": the swapfile's first physical extent is
  **199946240** (`sudo filefrag -v /swapfile`). That is the `resume_offset` you'd need.
- `/sys/power/image_size` = 6327451648 (~6.3 GB). Image fits in 20 GiB with wide margin.

### 6.2 ⭐ The one file that makes hibernate work

`/etc/modprobe.d/nvidia-power-management.conf`:
```
options nvidia NVreg_PreserveVideoMemoryAllocations=0
```

> ⚠️ **NEVER DELETE THIS FILE.** The parameter's default is `2` = "auto-enable when
> `UseKernelSuspendNotifiers` is on" — which it is. Deleting the file does not disable
> the behaviour, it re-enables the **broken** one. It must be explicitly `0`.

**Why:** with `Preserve…` on, the driver routes power management through a legacy procfs
interface that the 610 open module does not expose. The failure is on the **resume** leg:
the image is written and read back correctly, then `nv_pmops_freeze` returns `-5`, the
image is discarded, and the machine cold-boots as though hibernation never happened.
On 610-open, `NVreg_UseKernelSuspendNotifiers=1` (already the default) handles VRAM
save/restore instead, so nothing is lost by turning `Preserve…` off.

**Verify from `/proc`, never from the file** — and re-verify after every kernel upgrade
and every `limine-update`:
```bash
grep -iE 'preserve|suspendnotif' /proc/driver/nvidia/params
# want:  PreserveVideoMemoryAllocations: 0
#        UseKernelSuspendNotifiers:      1
```

`NVreg_TemporaryFilePath` is **not needed** on 610.57.04 — it already defaults to
`/var/tmp`, and it is only consulted when VRAM preservation is on, which is now off.

### 6.3 Why RTC wake is dead (evidence, 2026-08-20)

Two independent confirmations:

1. **In s2idle, 0/2 trials.** Both suspends entered s2idle correctly
   (`PM: suspend entry (s2idle)`, `Timekeeping suspended for 140.084 s` / `156.998 s`).
   Both alarm times fell inside those unbroken blocks. Neither woke. Trial 1's alarm was
   still latched, unfired, 89 seconds past its own fire time.
2. **While awake, it fires perfectly.** `rtcwake -m no -s 60` → 75 s later `alarm_IRQ`
   had flipped `yes` → `no` and `wakealarm` had self-cleared, exactly on schedule.

So the alarm arms correctly and fires correctly in S0 — it simply cannot rouse the
platform out of s0i3. Corroborated by boot-time dmesg:
`rtc_cmos PNP0B00:00: RTC can wake from S4` — S4, not S0ix.

`use_acpi_alarm` reads `Y` with no kernel parameter set, i.e. the AMD/BIOS-year quirk
force-enables it. Whether `rtc_cmos.use_acpi_alarm=0` can override the quirk is untested.

**The older explanation — "SMU firmware 64.44 < 64.53, so `amd_pmc` declines to attempt
the handoff" — is contradicted.** Something *is* attempted; the alarm is armed and fires.
The conclusion (no RTC timer) stands; the stated mechanism was wrong.

### 6.4 `_BTP` — the only wake path that works from s0i3

The ACPI `_BTP` battery trip point is EC-driven, a different hardware path from the RTC.
Pre-reinstall sessions recorded it waking the machine from s0i3 with ±1 min accuracy
across 4 self-wakes. **Not yet re-confirmed on this install.**

systemd implements this natively in `suspend-then-hibernate`: low-battery alarms (ACPI
`_BTP`) are tried first, and the system is woken by the ACPI low-battery signal and then
hibernated. With no `HibernateDelaySec=` set, the trip is placed near depletion (~5 %),
so it is a **"don't lose state when the battery dies" backstop, not a timer** — and it
writes to the SSD only on deep discharge, not on every lid close.

Relevant reference values: `BAT0/alarm` default is `8992000` µWh (~13.9 %).

### 6.5 Known unsolved: the lid-closed rollback (pre-reinstall, not yet re-tested)

After a `_BTP`-triggered wake from s0i3 **with the lid closed**, a subsequent
`systemctl hibernate` reached the final checkpoint then aborted with
`PM: hibernation: Wakeup event detected during hibernation, rolling back.` and
`NVRM: PM suspend notifier failed: 0x11`. The rollback wedged the NVIDIA driver — every
later suspend aborted in ~127 ms at ~45 W until a hard power-off; `reboot` hung.
Reproduced twice pre-reinstall. Same hibernate succeeded lid-**open** after an identical
`_BTP` wake, and lid-**closed** when no `_BTP` wake preceded it.

This is kernel bug 218634, reported on unrelated Intel and AMD hardware, intermittent
for those users too. Standard fix: find the wakeup-enabled device spuriously asserting
and disable it. **Only one of ~15–20 wakeup-capable devices was ever checked here.**

Native `suspend-then-hibernate` may be architecturally immune, because the transition
happens inside a single `systemd-sleep` invocation with sessions still frozen — but that
is an inference, not a test result.

⚠️ The designated positive control for this bug
(`rtcwake -m no -s 45 && systemctl hibernate`) **cannot work** — RTC alarms don't fire
in s0i3. A new instrument is needed before this bug can be investigated properly.

## 9. Testing notes that cost real time to learn

1. **`systemctl hibernate` returns immediately.** Anything chained after it with `;` or a
   newline runs *before* the machine goes down. Issue it last; check from a fresh prompt.
2. **SSH session survival is the cheapest genuine-resume proof.** TCP state lives in the
   image — a cold boot kills the session, a resume does not.
3. **But neither SSH survival nor `boot_id` distinguishes resume from rollback.** Only the
   journal, or physically watching the machine power off, separates those two.
4. **Firefox and Kate are useful secondary evidence.** After a cold boot Firefox *reloads*
   pages and Kate loses unsaved buffers. Neither happening indicates a real resume.
5. **`/sys/power/pm_test` never resets itself.** A real hibernate after a dry run is
   silently another dry run. Always confirm `[none]` first.
6. **`pm_test` cannot detect resume-leg bugs.** It runs inside the booted system and never
   reaches an initramfs — it could not have caught the NVIDIA `-5` failure.
7. **A stale `rtc0/wakealarm` did NOT block suspend** on this machine, contradicting older
   notes. Clear it anyway for hygiene, but it is not a blocker.
8. **Never measure battery drain above ~95 % charge** — the gauge is non-linear there and
   `energy_now` can read *rising*. Use the 60–80 % band.
9. **Measure in watts, not percent.** 1 % ≈ 648 mWh.
10. **A 10-minute drain test is below the noise floor.** At ~0.58 W it consumes ~97 mWh
    ≈ 0.15 % of capacity. Allow 60+ minutes for a usable number.
11. **`nvidia-smi` wakes the GPU.** Judge dGPU state from
    `/sys/bus/pci/devices/0000:01:00.0/power/runtime_status` instead.
12. **Wait ≥2 min after resume** before judging dGPU runtime state.
13. **`runtime_suspended_time` uses monotonic time**, which is frozen during s2idle — it
    will read far too low. Not a fault.
14. **Never `systemctl restart systemd-logind` on a live desktop.** It creates duplicate
    seat0 sessions and a lock→unlock→freeze loop that survives reboots. Use
    `daemon-reload` and reboot.
15. **systemd drop-ins merge by filename across all directories.** `/etc` only wins for
    *identical* filenames — a `10-foo.conf` in `/etc` loses to `10-nvidia-bar.conf` in
    `/usr/lib` because `f` < `n`. Use `60-`–`90-` prefixes; confirm with `systemctl cat`.
16. **The power button is under the lid.** With the lid shut, `_BTP` is the only wake
    source. Design lid-closed tests accordingly.
17. **Never press the power button during an image write** (~35 s).
18. **`/mnt/data` does not exist on this machine.** Save diagnostics to `~/`.
19. **Change one variable at a time.**
